## 一、计划执行保证（4 道关卡）

每一步开发都必须经过以下 4 道关卡，不允许跳过。

### 关卡 1：开工前宣读

每一步开始前，从 `DEVELOPMENT_PLAN.md` 读出本步的：
- 做什么（范围）
- 产出什么（交付物）
- 验收标准是什么（逐条列出）

用户确认范围无误后，才开始动手。

### 关卡 2：进行中一步一反馈

关键节点即时反馈，不攒到最后：
- 代码编译通过
- 界面首次跑起来
- 核心功能实现
- 内容写完一批

反馈时附截图或编译输出，不只是文字描述。

### 关卡 3：完成后逐项验收

对照本步的验收标准，一条一条打勾：
- 全部通过 → 交付，进入下一步
- 有一条未通过 → 继续改，不蒙混过关，不交付半成品

### 关卡 4：计划外变更必须先报批

如果开发过程中发现计划需要调整（技术方案走不通、需要加功能、发现遗漏），必须先说明：
1. 为什么要变（原计划有什么问题）
2. 变什么（具体调整内容）
3. 影响什么（对后续步骤、时间、范围的影响）

用户确认后才修改计划，不擅自偏离。

## 二、Bug 处理标准流程（5 步）

发现任何 bug（代码 bug、内容错误、UI 问题、交互问题），必须按以下 5 步处理，不允许「改了就行」。

### 第 1 步：复现与定位

- 先稳定复现 bug（记录复现步骤、输入、预期结果、实际结果）
- 追到根因：不是「现象是什么」，而是「代码/内容/设计层面为什么会这样」
- 根因必须能用一句话说清楚

**产出：** 根因说明

### 第 2 步：影响分析

- 这个根因还会影响哪些场景？
- 列出所有受影响的用例（不只是撞到的那一个）
- 评估严重程度（阻断性 / 影响功能 / 体验问题 / 文案错误）
  - 阻断性：应用无法启动、核心功能不可用 → 未清零则 CHECKLIST 结论为"不通过"
  - 影响功能：某功能异常但有替代方案 → 未清零则 CHECKLIST 结论为"有条件通过"
  - 体验问题 / 文案错误：不影响功能 → 可延期修复，但需记录

**产出：** 影响范围清单

### 第 3 步：根因修复

- 从根因入手修复，不打表面补丁
- 如果发现是设计层面的问题，回到设计改，不在代码里绕
- 最小化修改：只改必须改的地方，不顺便「重构」「优化」「调整风格」

**产出：** 修复方案 + 修改的文件/行号

### 第 4 步：回归验证

修复后必须验证：
1. **bug 场景**：确认修复有效（bug 不再出现）
2. **相关场景**：跑全部受影响的用例，确认没有副作用
3. **全量回归**：跑当前阶段所有已通过的验收项，确认没有引入新 bug
4. **边界条件**：测试空输入、极值、特殊字符等边界情况

**产出：** 回归测试结果（全部通过才完成）

### 第 5 步：记录归档

将以下信息记录到独立的 [BUG_LOG.md](BUG_LOG.md) 文件（不在本文档内追加，避免本文档越来越长）：
- bug 编号、发现日期
- 现象描述
- 根因分析
- 影响范围
- 修复方案
- 回归验证结果

**目的：** 避免以后再犯同类问题，也便于追溯。BUG_LOG.md 按编号追加，每条一个小节。

## 三、系统性修复保证（3 个机制）

### 机制 1：修复前先写测试用例

在改代码之前，先写一个能稳定复现这个 bug 的测试/验证步骤：
- 确认测试失败（bug 存在）
- 修复后跑这个测试，确认通过
- 这个测试一直保留，每次回归都跑

**对于内容类 bug：** 先记录「错误内容是什么、正确内容应该是什么」，修复后对照验证。

### 机制 2：同类问题全局排查

修完一个 bug，全局搜索是否有类似的代码模式/逻辑/内容写法：

| 修了什么 | 全局排查什么 |
|---------|------------|
| 一个指令的参数顺序错误 | 所有指令的参数顺序是否都对 |
| 一个参数解释错误 | 同类型元器件的其他参数是否有类似错误 |
| 一个 UI 布局问题 | 其他页面是否有同样的布局问题 |
| 一个错误匹配模式不对 | 所有错误的 errorPattern 是否都准确 |
| 一段代码有内存泄漏 | 同类写法的其他地方是否也有泄漏 |

有就一起修，不留下「定时炸弹」。

### 机制 3：全量回归

每修一个 bug，跑一遍**当前阶段所有已通过的验收项**：
- 第 1 步修了 bug → 跑第 1 步全部验收项
- 第 3 步修了 bug → 跑第 1~3 步全部验收项
- 不只是「我改的那个功能没问题」，而是「所有已经做好的功能都没问题」

> **备注**：MVP 阶段内容少，全量手动回归可接受。到第三阶段（150+ 内容）后，建议引入自动化测试或抽样回归（在 ROADMAP 第三阶段"体验优化"中规划），避免回归成本越来越高。

## 四、不引入新 Bug 的保证（4 条原则）

### 原则 1：最小化修改

修 bug 时只改必须改的地方：
- 不顺便重构
- 不顺便优化性能
- 不顺便调整代码风格
- 不顺便加新功能

那些放到单独的步骤里做，和 bug 修复分开。**一次提交只做一件事。**

### 原则 2：修改后必须编译+运行

代码类修改必须：
- 重新编译，确认无警告、无错误
- 实际运行，确认应用能正常启动
- 手动操作修改涉及的功能路径

不允许「改了代码没编译就说修好了」。

### 原则 3：对照修改前后的行为

修改前是什么行为，修改后应该是什么行为，逐条对比：
- 正常场景：行为是否符合预期
- 异常场景：错误处理是否正常
- 边界场景：极值/空输入是否正常

### 原则 4：边界条件检查

修完后必须测试边界情况：
- 空输入、空字符串、nil
- 极值（最大/最小值）
- 特殊字符（中文、空格、符号）
- 并发/快速重复操作

这些地方最容易引入新 bug。

## 五、验证手段（按类型）

| 类型 | 验证方式 |
|------|---------|
| **代码类**（Swift） | 编译无警告 + 实际运行 + 手动操作关键路径 + 边界条件测试 |
| **内容类**（JSON 指令/参数/错误） | 交叉验证（查 LTspice 官方文档 / 实际跑仿真确认）+ 用户审核 |
| **UI 类** | 截图确认 + 用户目视验收 + 不同窗口尺寸测试（最小/最大/默认） |
| **交互类** | 手动操作全流程 + 键盘/鼠标两种方式都测 + 异常输入测试 |
| **性能类** | 开发目标：启动时间 < 1 秒 + 搜索响应 < 10ms + 内存占用 < 50MB（空闲）。发布下限见 CHECKLIST.md（<2s / <100ms / <100MB） |

## 六、Bug 记录模板

> 实际 Bug 记录归档在独立的 [BUG_LOG.md](BUG_LOG.md)，以下为记录模板，每条 bug 修复后按此格式追加到 BUG_LOG.md。

每个 bug 修复后按以下格式记录：

```
### Bug-001：[简短标题]
- 发现日期：YYYY-MM-DD
- 严重程度：阻断性 / 影响功能 / 体验问题 / 文案错误
- 现象：[一句话描述 bug 现象]
- 复现步骤：1. ... 2. ... 3. ...
- 根因：[一句话说清楚为什么会这样]
- 影响范围：[列出所有受影响的场景]
- 修复方案：[改了什么，怎么改的]
- 修改文件：[文件路径 + 行号]
- 回归验证：[列出验证的场景，全部通过]
- 同类排查：[是否排查了同类问题，结果如何]
```
