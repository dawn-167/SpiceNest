# SpiceNest 开发防错建议清单

> 版本：0.1 | 日期：2026-08-27
> 目的：围绕"减少开发过程中可能出现的错误"，提出可落地的防错机制。
> 定位：建议文档，不修改任何现有文档；是否采纳、由谁落地由项目方决定。
> 关联：与 [QUALITY_ASSURANCE.md](QUALITY_ASSURANCE.md)（流程保证）互补——本文档聚焦"机器能替你兜住的错误"。
>
> **规范来源**：核心防错机制已纳入 Nexus 通用开发规范 [`Nexus/DEVELOPMENT_STANDARDS.md`](file:///Users/dawnli/Documents/Nexus/DEVELOPMENT_STANDARDS.md)（第三部分：防错机制）。本文档为 SpiceNest 项目特定的防错建议，包含项目特定的脚本规划和落地时机。

---

## 一、核心判断

流程文档（QA 关卡、Bug 五步、CODE_STANDARDS 自查）已经解决了"靠人自觉"的部分。
接下来防错增量主要来自**把"人工勾选"变成"脚本验证"**：

- 人查 20 条内容可行，查 150 条必漏 → 交给脚本
- 公式表达式看着对 ≠ 计算函数算得对 → 用已知值断言
- 改完搜索算法"好像还能搜" ≠ 没回归 → 固化用例集
- 文件被覆盖后无法恢复 → 版本控制兜底

---

## 二、风险分级

| 风险源 | 严重度 | 发生频率 | 现有兜底 | 缺口 |
|--------|--------|---------|---------|------|
| 内容准确性（指令/参数/错误/公式） | 高 | 高 | 用户逐条核对（G2） | 150+ 条后人工必然漏检 |
| 公式计算函数写错/单位换算错 | 高 | 中 | 无（只有"看起来对"） | 无自动化断言 |
| 搜索回归（加内容后旧的搜不到） | 中 | 中 | 无（验收表验完即弃） | 无回归用例集 |
| 文档/代码丢失、误覆盖 | 高 | 低 | 无（编辑器本地历史碰运气） | 无版本控制 |
| .asc 拓扑片段写错 | 高 | 中 | "在 LTspice 中实际测试过"（靠自觉） | 无强制验证机制 |

## 三、防错清单（按优先级）

### P0：立即可做（防丢数据）

#### 1. 立即 `git init` 并每步提交

- **防什么错**：文件误覆盖、误删除、改坏后无法回滚（本次 QUALITY_ASSURANCE.md 被覆盖事件即教训）。
- **怎么做**：项目根目录 `git init`，按 CODE_STANDARDS 6.5 规范提交（一次提交一件事、`[模块]` 前缀、提交前编译通过）。
- **落地点**：MVP 第 1 步框架搭建时同步做；现有 14 份文档先做一次初始提交。
- **验收**：`git log` 有历史，任何文件可 `git checkout` 恢复。

---

### P1：写内容前就该有（防内容错误——最大风险源）

#### 2. 内容 JSON 机器校验脚本（`scripts/validate_content.sh`）

- **防什么错**：
  - JSON 语法错误（中文引号、全角符号、尾逗号、UTF-8 BOM）——高频低级错误
  - id 重复、`related` 引用死链——content-guide 9.1 有要求但靠人查必漏
  - 硬性规则：tags ≥ 3、summary ≤ 40 字、id 命名格式、required 字段齐全
- **怎么做**：用 python3 写一个校验脚本，遍历 `content/` 下所有 JSON，输出违规清单。
- **落地点**：MVP 第 3 步（第一批内容数据）前写好；此后每批内容写完跑一遍。
- **验收**：对 20 条示例内容跑出 0 违规；故意注入一个死链能报出来。

#### 3. 公式计算器"验证用例"字段

- **防什么错**：公式表达式正确但计算函数写错、单位换算错（如 m 与 meg 混淆——SPECIFICATION 已点名这是 LTspice 最常见易错点）。
- **怎么做**：在公式 JSON 中增加可选字段：
  ```json
  "verify": {
    "inputs": { "R": 10000, "C": 1.0e-7 },
    "expected": 159.15,
    "tolerance": 0.01
  }
  ```
  校验脚本读取 verify 字段，用已知值断言计算结果（R=10kΩ、C=100nF → fc≈159.15Hz）。
- **落地点**：content-guide 6.x 公式规范补充该字段说明；CalculatorService 实现时同步验证。
- **验收**：每个带计算器的公式都有 verify 字段；脚本能自动算出并比对。

#### 4. 搜索回归用例集（`scripts/search_cases.txt`）

- **防什么错**：加了新内容/改了搜索算法后，旧的能搜到变成搜不到（回归）。
- **怎么做**：把 DEVELOPMENT_PLAN 第 4 步的验收表固化成一个常驻用例文件：
  ```
  tran           → command-tran + error-time-step-too-small
  收敛           → 多个收敛类错误
  未知           → unknown-parameter + unknown-device
  仿真           → .tran .ac .op 等多个指令
  xyz不存在      → 空结果
  ```
  每批内容写完、搜索算法每次改动，跑一遍比对结果。
- **落地点**：MVP 第 4 步（搜索服务）验收时创建；挂到 QA 机制 3"全量回归"中。
- **验收**：所有用例关键字都能命中预期 id 集合。

---

### P2：开发中逐步落地

#### 5. Services 层命令行测试真正落地

- **防什么错**：模型/SearchService/ContentLoader 逻辑错误在 UI 层才暴露，排查成本高。
- **怎么做**：CODE_STANDARDS 1.3 已承诺"无 UI 依赖，可在命令行跑测试"——兑现它。做一个极简测试入口（`swiftc` 编译 + 断言 print，不引入 XCTest），覆盖 MVP 第 2~4 步的纯逻辑。
- **落地点**：MVP 第 3/4 步验收时随产出提交。

#### 6. .asc 拓扑片段强制验证

- **防什么错**：LTspice 网表格式繁琐、版本差异大，是人最容易写错、最难人工验证的类型。
- **怎么做**：① 拓扑放第三阶段（ROADMAP 已如此安排）；② 每条拓扑过 G2 门禁前，必须真实打开 LTspice 验证可仿真，并把验证结果截图归档——不接受"看起来对"。
- **落地点**：content-guide 8.x 拓扑规范加"验证证据"要求；CHECKLIST 1.8 已有对应项，执行时落实。

#### 7. 错误匹配防版本差异

- **防什么错**：LTspice 不同版本报错文案有差异（如 "Time step too small" 拼写），精确匹配会漏。
- **怎么做**：errorPattern 匹配统一用"包含匹配 + 同义词标签"，而不是精确匹配；同一条错误的不同拼写进 tags。
- **落地点**：SearchService 实现时按 content-guide 5.4 的思路落实。

#### 8. 发布检查前移

- **防什么错**：CHECKLIST 是发布前才跑，很多项（搜索 <100ms、无强制解包、边界测试）其实每步就该验，攒到最后容易返工。
- **怎么做**：DEVELOPMENT_PLAN 每步验收里显式挂上对应的 CHECKLIST 项（如第 4 步挂搜索响应、第 5 步挂 UI 项），边做边勾。
- **落地点**：MVP 执行时对照落实。

## 四、落地优先级建议

| 批次 | 事项 | 时机 |
|------|------|------|
| 第一批（开工前） | 1. git init + 初始提交 | 现在就做 |
| 第二批（MVP 第 3 步前） | 2. JSON 校验脚本；3. 公式 verify 字段；4. 搜索回归用例集 | 写第一批内容前 |
| 第三批（MVP 第 3~4 步） | 5. Services 命令行测试 | 随模型/服务开发 |
| 第四批（第三阶段） | 6. .asc 强制验证；7. 错误匹配实现；8. 发布检查前移 | 随拓扑/体验优化 |
